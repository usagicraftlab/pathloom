## 1. 目的と確定要件

### 1.1 何を追加するか

パス生成の前段に、曲線・サーフェス・ソリッドを作図・編集・保存できるCAD工程を設ける。コマンドで作業を開始し、画面上の選択・スナップ・数値入力で形状を決める。スケッチには幾何拘束と寸法拘束を付けられる。寸法変更を作成履歴に沿って後段へ反映する。

操作方式はRhinoの公開された一般的な作図フローを参考にするが、Pathloom独自のコード・画面・アイコン・説明文で実装する。拘束の可視化はFusionのように分かりやすくするという要求であり、同製品の画面や素材の複製要求ではない。権利面は第14章に従う。

### 1.2 画面の配置

現在の3つの工程アイコンの**左にCADを追加**し、左から次の4工程にする。

| 順番 | 表示名案 | 役割 |
| --- | --- | --- |
| 1 | CAD／形状作成 | 今回追加。スケッチ、形状編集、作成履歴、形状保存 |
| 2 | パス生成（AI） | 既存の生成・コンポーネント編集 |
| 3 | パラメータ調整 | 既存のパラメータ編集 |
| 4 | 出力設定 | 既存の配置・印刷設定・G-code・プリンター送信 |

CAD工程の配置は**左＝コマンド、中央＝3Dビュー、右上＝操作設定、右下＝作成履歴**で固定する。コマンド欄を下部に移したり、履歴を左へ移したりしない。中央の3Dビューは4工程で共有する。

### 1.3 自由度の原則

1. 開いた曲線、開いたサーフェス、開いた複合面を正式な形状として扱う。閉じていないこと自体はエラーではない。
2. 一般のCAD形状には非平面、負のZ、印刷範囲外、印刷に適さない形状を許す。平面スケッチだけはそのスケッチ平面上で扱う。
3. 自己交差なども、入力・保存の段階で一律禁止しない。その形状を扱えない演算を実行したときに、当該演算の成立条件を説明する。
4. 形状を生成できる場合は、原則として警告だけで続行可能にする。警告による毎回の確認ダイアログは設けない。
5. 数学的に演算できない、参照先が特定できない、壊れた形状しか返せない場合だけ、その操作を停止する。元データを破壊しない。
6. 自動で閉じる、隙間を埋める、トリムする、ソリッド化する、許容差を拡大する、別の面を選び直す処理は、明示的な選択肢にする。
7. 未完成・拘束不足・失敗履歴を含む作業状態も保存できる。古い結果を現在の結果と偽って印刷に渡さない。
8. 幾何の成立条件、データ整合性、負荷制御、印刷条件を別々に判定する。印刷検証をCAD作図に使い回さない。

### 1.4 対象外

- メッシュモデリング、SubDモデリング、レンダリング制作、図面作成・レイアウト・Make2D・製図出力。
- Rhino／Fusionの完全互換、全コマンド・全オプションの網羅、独自ファイル形式・マクロの互換実装。
- クラウドアカウント、共同編集、オンライン形状ライブラリ、追加課金サービス。

CAD表示のための三角形分割、通常の陰影表示、面・エッジのハイライトは内部表示処理として必要。これは「メッシュ編集やレンダリング機能を追加する」こととは区別する。

## 3. CAD画面・操作フロー

### 3.1 左：コマンドパネル

- 上部にコマンド入力。英語名、日本語名、別名で検索できる。候補には短い独自説明と対象形状を表示。
- その下に、実行中のコマンド名、現在の手順、選択済み対象、次に指定すべきもの、選べるモードを表示。
- 下部に直近のコマンド実行ログ。これは右側の再計算可能な作成履歴とは別物。
- 例：`Rectangle` → 「作図方法：2コーナー／中心／3点」→「中心点を指定」→「コーナー、または幅・高さを指定」。
- コマンド欄は通常の操作入力。AIチャットへ毎回送信しない。AIによるコマンド作成は明示的に選ぶ別操作とする。

### 3.2 右上：操作設定・プロパティ

- コマンド実行中はその操作の数値・モード・入力対象・許容差を表示し、中央のプレビューと双方向に連動。
- 履歴を選択した場合は、その操作を同じ欄で再編集する。
- 待機中に形状を選択した場合は、名前、型、寸法、閉／開状態、関連する操作、表示／ロックを表示。
- 拘束付きスケッチを編集中は拘束・寸法・自由度・矛盾の一覧と編集操作を表示。
- 明示的な確定／キャンセルを設ける。未確定入力と保存済み設定を区別する。

### 3.3 右下：作成履歴

- 操作名、対象形状、主要寸法、状態アイコンを並べる。例：`Rectangle · 60 × 40`、`Extrude · 25`、`Fillet · R2`。
- 選択すると対象・出力をハイライトし、右上に設定を表示。表示・非表示、名前変更、抑制、再試行、対象再指定、削除を提供。
- 独立した複数形状を扱えるようにし、同じ文書に複数の履歴分岐を保持する。単なる直線的な操作ログにはしない。
- 履歴順変更は依存関係が成立する場合だけ許す。最初は順変更を提供しなくてもよいが、依存関係を壊すドラッグは実装しない。
- エラー原因の操作と、原因待ちの後段を明確に区別する。
- 履歴パネルを物体一覧としても使えるよう、各操作の出力形状を展開して選択・可視性変更できる構成を推奨。

### 3.4 中央：ビュー・選択・入力

- 既存の3Dビューとカメラ操作を再利用。上／正面／右／透視、既存の方向キューブ、選択形状へFitを利用可能にする。
- オブジェクト・面・エッジ・制御点の選択を区別する。面を選ぶために形状を分解する必要をなくす。
- 先に選択してからコマンド、コマンド開始後に選択、両方をサポート。
- Shiftクリックで追加／解除。重なった対象は候補を提示し、面・エッジの選択モードを明示。選択中の対象を勝手に置換しない。
- 矩形選択は完全包含／交差選択を区別。CAD入力中のドラッグとカメラ回転が競合しないようにする。
- 作業平面はWorld XY／XZ／YZ、選択した平面、原点＋軸指定。スケッチは平面のローカル座標を保持。
- スナップは端点・中点・中心・交点・最近点を基本とし、垂線・接線も追加。対象別にON/OFF、候補の種類を画面に表示。
- 座標入力は絶対XYZ・直前点からの相対XYZ・方向に沿う距離を提供。初期単位はmm、角度は度。スケッチの寸法はローカル平面上で扱う。
- スナップ許容は画面上のピクセル距離、Join等の幾何許容差はモデル単位。両者を同じ設定にしない。

### 3.5 キーボードと工程切替

- Enter：コマンド候補確定／現在手順の決定／複数選択終了。待機中は前回コマンド再実行。
- Esc：現在の未確定操作をキャンセル。確定済み形状を消さない。
- Delete／Backspace：文脈に応じた選択対象削除。文字編集中には形状削除を発火しない。
- macOSのCmd+Z／Cmd+Shift+ZでUndo／Redo。プレビューの各フレームを履歴に積まない。
- 数値欄・コマンド欄への入力中は、既存ノード編集のショートカットを発火させない。
- 未確定操作中に別工程へ移るときは、確定／破棄／移動をやめる、を選べるようにする。未入力で無変更ならそのまま切替可能。
- 工程を戻したとき、CAD文書、選択、作業平面、パネル幅、カメラを不必要に初期化しない。既存プロジェクトの起動工程を一律CADへ変更しない。
- 初期幅の推奨値は左280px、右320px程度。左右と右上下の分割位置を変更・保持可能にする。1280×800でも設定・履歴へ到達できること。

## 4. コマンドと共通形状処理の関係

### 4.1 親子関係

共通の幾何演算を土台に、**CADコマンドと生成コンポーネントを並列の入口**として置く。CADコマンドが生成グラフ全体を呼び出す構造にしない。

- 共通演算：長方形、Join、押し出しなど、入力と設定から形状を作る処理。
- CADコマンド：対象を選び、クリック・数値で入力を集め、プレビュー・確定する薄い操作層。
- コンポーネント：接続済みの型付き入力から同じ演算を呼び出す入口。
- CAD履歴：演算ID・版・パラメータ・入力参照・出力IDを保持する依存グラフ。画面にノード接続を要求しない。
- 各CAD操作を自動的に生成コンポーネントへ変換しない。ユーザーが生成工程へ渡すときに境界を設ける。

### 4.2 コマンドを育てる

主目的は複雑なマクロの自動生成ではなく、**2コーナーRectangleしかないときに中心指定Rectangleを追加できる**こと。

実装推奨のコマンド定義：安定ID、版、独自表示名、別名、説明、対応形状、入力手順、設定スキーマ、プレビュー方法、呼び出す共通演算、履歴への記録形式。

例：`rectangle.center`は中心点と対角点から幅・高さ・平面を求め、共通の長方形生成を呼ぶ。`rectangle.twoCorners`も同じ生成処理を使う。中心モードでは中心が固定された状態で幅・高さを再編集できるよう、入力意味も履歴に残す。

標準コマンド内の作図モードとして登録でき、必要なら`CenterRectangle`のような別名で直接呼べる。単なるモード追加のために新しいWorker・AI推論・新規生成グラフを必須にしない。

「コマンドを追加／編集」から、既存定義の複製、入力順・既定値・表示設定の編集、試用、名前付き保存、版の更新ができる。既存の明示的AI編集経路も利用できるようにする。AIは許可済み演算の構造化定義を生成し、任意のネイティブコードやネットワーク処理を実行させない。

標準定義は上書きせずユーザー定義として保存。使用済みプロジェクトは利用した版を固定し、新版へは明示的に更新する。全ライブラリを毎回AIへ送らない。入力・出力・参照型を検証する。

## 5. スケッチと拘束

### 5.1 自由作図との両立

自由な3D曲線作図と、平面上の拘束付きスケッチを両方提供する。すべての形状をスケッチへ押し込まない。拘束不足でも正常に使える。スケッチ平面の変更はワールド形状との関係を明示して行う。

### 5.2 拘束の目標範囲

| 種類 | 振る舞い |
| --- | --- |
| 一致 | 点同士、点と曲線を一致させる。参照対象と関連する自由度を保持 |
| 水平・垂直 | スケッチのローカル軸に対して適用 |
| 平行・直交 | 対応する直線／接線方向の関係を保持 |
| 接線 | 線・円弧・曲線の対応可能な組合せ。端点／接触箇所を指定 |
| 同心・等値 | 円／円弧の中心、線の長さ、円の半径等を対象に応じて等しくする |
| 固定 | 選択点や要素の位置・形状を固定。解除可能 |
| 対称 | 指定した軸に対する要素・点の対称関係 |
| 距離・長さ | 点間距離、水平／垂直距離、線長を寸法として編集 |
| 半径・直径・角度 | 対応図形の値を直接編集。駆動寸法と参照寸法を区別 |

拘束の表示はPathloom独自の記号・色・説明で作る。選択時に該当箇所を強調し、右上から編集／一時抑制／解除可能にする。自動拘束は候補提示を基本とし、暗黙に大量追加しない。自動付与を有効にした場合は設定と付いた拘束を見える状態にする。

### 5.3 解けない場合

- 未拘束：自由度を表示し、そのまま作図・保存・立体化可能。
- 冗長：満たせるが重複する拘束を警告。不要なものを選んで解除できる。
- 矛盾：衝突候補を強調。今回の拘束を適用せず、直前の解を保つ。未確定の指定内容は修正・保存可能。
- 解が複数：直前形状に連続する解を優先。突然反転する場合はユーザーが向き・解を選べるようにする。
- ドラッグ中は関係するスケッチだけを解く。完全拘束を必須にしない。

ソルバーは実装初期に試作評価し、必要な幾何・寸法拘束、macOS、ライセンス、実測性能で選定する。ソルバー未評価のまま「すべて対応済み」としない。採用時の条件は第14章に従う。

## 6. コマンドの目標範囲と具体的な動作

本章は機能単位で整理した目標一覧。括弧内は機能理解のためのRhino参照名であり、Rhinoのコード・ヘルプ文・アイコン・メニュー配列を複製する指示ではない。英語表示名案は実装時にPathloomの用語へ統一する。一般的な幾何用語はそのまま使える方針とし、名称全体の権利上の無条件な安全性を断定しない。

全コマンド共通：入力選択→数値／モード設定→プレビュー→確定→履歴記録。対応外の組合せは、必要な入力と代替操作を説明する。処理できないコマンドを、外見だけのボタンやダミーの成功表示で埋めない。

### 6.1 曲線・作図補助の作成

| ID | コマンド名案（参照） | 入力・設定・結果 |

### 6.8 Joinの詳細な成功・失敗規則

- Curve同士とSurface同士を同じ`Join`入口で対象型に応じて処理。Curve＋Surfaceの混在は適切な選択へ誘導する。
- 許容差の初期推奨値はモデル単位mmで0.01。操作ごとに変更し、履歴に保存。モデルの大きさだけで無断拡大しない。
- Curveは端点接続による一本または複数の連結グループを作る。途中で交差するだけでは接続せず、必要ならSplitを案内。
- Surfaceは境界を位相的に接続。接続しただけで一枚の基底面になるとは限らず、複合面として扱う。基底面を融合する処理は別の明示操作。
- 離れた境界を延伸・変形して合わせない。つながらない境界をハイライトし、測れる場合は実距離と現在の許容差を表示。
- 選択対象の一部だけつながる場合は、結果のグループ数と残る形状をプレビュー。ユーザーが確定すれば有用な部分結果を保持。
- 分岐や複数候補で一意に決まらない場合は対象を選び直せるようにし、選択順だけで意図しない接続をしない。
- 閉じた曲線にならなくても、また閉じたソリッドにならなくても、Joinとして成立した結果は成功。

## 7. 正確な形状データ・履歴・参照

### 7.1 形状の正本

- Curveは解析曲線／NURBS／複合曲線の正確な定義、Surface・Solidはトリムと位相を持つB-repを正本にする。
- 表示用の三角形やポリラインは派生キャッシュ。フィレット・Join・再編集の入力を表示メッシュへ置換しない。
- 開いた面、閉曲面、開いたShell、閉体積Solidを区別。円筒面が周方向に閉じていても、端が開いていればSolidとはしない。
- 既存の生成側が点列しか受け取れない場合、明示した近似精度で変換するアダプターを挟む。正本を捨てない。

### 7.2 文書モデル案（実装推奨）

```text
CadDocument
  schemaVersion / units / tolerance
  entities[] : entityId, kind, name, producerFeatureId, revision,
               geometryRef, visibility, validity, diagnostics
  sketches[] : sketchId, plane, elements, constraints, dimensions
  features[] : featureId, operationId, operationVersion, inputs,
               parameters, outputEntityIds, status, lastValidRevision
  assets{}   : contentHash -> exact geometry payload
  commandDefinitions[] : project内で必要なユーザー定義と版
  uiState    : activeStage, camera, selection, workPlane, panelSizes
```

フィールド名は既存モデルに合わせて変更可能。ただし安定ID、演算の版、依存参照、診断、正確な形状、必要なユーザー定義の保持を省かない。履歴とUndoスタックは別にする。Undoスタックを唯一の形状保存にしない。

### 7.3 依存関係と再計算

- 例：スケッチ寸法→Rectangle→Extrude→Fillet→CAD出力→既存パス生成。
- パラメータ変更は当該操作と下流のみをdirtyにする。独立した形状を再計算しない。
- 連続ドラッグの要求をまとめ、最新revisionだけを採用。古い応答が戻っても上書きしない。
- 計算済み／警告付き／再計算中／失敗／上流待ち／抑制を区別する。
- 閉じた輪郭を作るためだけの不要な拘束は追加しない。作図方式に固有の幾何関係とユーザー追加の拘束を見える形で保持。
- 過去のパラメータ再編集もUndo可能な一つのトランザクションとして扱う。

### 7.4 面・エッジ参照の維持

配列indexや表示三角形番号だけを、永続的な参照として保存しない。形状編集により面数やエッジ順が変わるため、次を実装する。

1. 生産元feature・出力entity・subshapeの安定参照を持つ。
2. カーネルが提供するModified／Generated等の対応情報を優先して更新する。
3. 必要に応じて面種別、所属、隣接、位置・向き等で照合するが、許容差と曖昧さを評価する。
4. 複数候補や参照消失を無理に自動解決しない。「参照を選び直す」で候補をハイライトする。
5. 再指定で履歴の入力参照を更新し、その後段だけ再計算する。

対象を失ったFilletが別のエッジへ黙って移ることを禁止する。完全な追従を保証できないケースを、分かる失敗と修復可能な状態にする。

### 7.5 ソルバー・カーネルの責務

拘束ソルバーはスケッチの未知数と関係を解き、CADカーネルは曲線・面・B-repの演算を行う。OCCTがスケッチ拘束・全履歴・安定参照をすべて自動提供すると仮定しない。既存の面移動履歴を、そのまま汎用履歴として扱わない。

## 8. 警告・エラー・解決への導線

### 8.1 判定と表示

| 状態 | 処理・表示 |
| --- | --- |
| 情報 | 開いた面、拘束不足など正常な状態。情報アイコンのみ。失敗扱いしない |
| 警告 | 結果は使えるが、近似・未接続・自己交差等に注意。続行・確定・保存可能。対象箇所に控えめな表示 |
| 操作失敗 | 要求した演算が成立しない。元の入力と最後に成功した結果を保ち、該当操作だけを止める |
| 上流待ち | 原因の操作が失敗／未解決のため更新できない。原因操作へのリンクを表示し、別のエラーを大量に出さない |
| キャンセル・資源制限 | 計算中断、メモリ等の上限。形状の幾何エラーと区別。精度・対象数を変える／再試行へ誘導 |

警告は原則として非モーダル。履歴アイコン・右上の診断欄・対象形状のマーカーから詳細を開く。色だけで区別せず、短い状態名とアイコンを併用する。

### 8.2 メッセージの必須内容

1. どの操作が、何に対して成立しなかったか。
2. 分かっている原因。推定は推定と明記し、特定できない場合はそう伝える。
3. 問題の場所：面・エッジ・点・拘束・履歴を選択／ハイライトするボタン。
4. 次にできる具体的な操作を1〜3個。クリックすると対応する編集状態へ入る。
5. 元に戻す／今回の変更を取り消す導線。
6. 技術詳細は折りたたみ表示。通常のユーザー導線にスタックトレースを出さない。

例：

> フィレットの対象が見つかりません。押し出しの形状変更で、以前指定したエッジを特定できなくなりました。
> ［対象を選び直す］［押し出しを開く］［今回の変更を取り消す］

> 2つの境界が接続されていません。最短距離は0.08mm、現在の許容差は0.01mmです。
> ［境界を表示］［形状を編集］［許容差を変更］

> 半径5mmのフィレットを作成できませんでした。選択したエッジ周辺で形状が成立しません。
> ［半径を編集］［対象を選び直す］［取消］

成立可能な最大半径を計算していない場合は、その値を断定しない。「小さくすれば必ず直る」と保証しない。

```json
  "severity": "error",
  "featureId": "feature-fillet-1",
  "entityIds": ["body-1"],
  "subshapeRefs": ["edge-ref-1"],
  "causeFeatureId": "feature-extrude-1",
  "message": "フィレットの対象エッジを特定できません。",
  "actions": ["reselectReference", "editCause", "revertEdit"],
  "details": {"reason": "ambiguous-or-missing"}
}
```

エラー文の文字列一致でUIを分岐させない。診断IDと対応アクションを共有契約にする。ネイティブの元エラーは開発用詳細へ保持するが、認証情報・個人の絶対パスを不用意に表示・保存しない。

### 8.4 最後に成功した形状の扱い

最後の成功形状は表示・修復のために残せる。ただしゴースト表示や「更新前の形状」ラベルで現在の設定結果と区別する。下流の生成には最新の正常revisionだけを渡す。

失敗した設定と履歴を含めた作業保存は可能。ファイルに、現在の要求設定・診断・最後に成功した形状の版を区別して保存する。「保存できないので直しようがない」状態にしない。

カーネルが壊れた形状を返した場合は元の正本を置換しない。表示できる元形状・未確定設定・診断を保持し、偽の正常B-repを保存しない。

## 9. プロジェクト保存・形状保存・コマンド保存

### 9.1 プロジェクト全体

既存のOpen／Save／Save asを使い、CAD文書、スケッチ、拘束、寸法、履歴、正確な形状、生成への参照、使用したユーザーコマンド定義、必要なUI状態を保存する。

推奨方式：`.pathloom`のversion 2を追加し、version 1→2の読込移行を実装する。別方式を選ぶ場合も旧プロジェクトの読込互換を必須とする。旧検証を通すためだけにversion 1へ意味の違うフィールドを黙って詰め込まない。

- 正確な形状データをcontent hash等で重複排除。独立した出力で共有できる定義は一度だけ保存。
- ローカルキャッシュのassetId／絶対パスだけに依存しない。別の同等環境へファイルを移しても必要形状を再構成できるよう正本を内包する。
- 既存STEPのローカル資産参照も移行時に検出し、埋め込み可能なら移行。元資産がない場合は「表示のみ／編集不可」を表示し、STEP再指定へ誘導。
- 履歴を再計算できない環境でも、保存済みの表示用データと診断で内容を確認可能にする。表示キャッシュを編集可能な正本と偽らない。
- スケッチの未確定寸法は文字列draft等に分け、NaN／Infinityを正確な形状データへ混入させない。
- 保存は一時ファイルと置換等で原子的に実行。保存失敗時に元ファイルを壊さない。
- 読込は構造・参照・版を検証してから現在の作業を置換。未知の演算版は元ファイルを保護し、読取可能な範囲と不足条件を表示。
- 認証・Keychain情報・Codexトークン・プリンター秘密情報は保存対象外。

### 9.2 選択形状をライブラリへ保存

ユーザーは選択したCurve／Surface／Solid／複数形状を、名前・説明・タグ付きで保存し、後からCAD文書へ挿入できる。

推奨：`Shape Library`を既存コンポーネントライブラリのストレージ・版管理基盤と共通化し、項目種別だけ分ける。内部実装を共有しても、UIで形状とコマンドとコンポーネントを取り違えない。

保存方式：

- **形状だけ**：正確な形状、単位、基準点、名前を保存。挿入先では独立した編集可能な形状になる。
- **作成履歴付き**：必要な依存履歴・スケッチ・拘束・コマンド定義を閉包として保存。挿入時はIDを再発行し、内部参照だけを付け替える。

初期値は「形状だけ」を推奨し、保存時に履歴付きも選べるようにする。挿入後の編集が保存済みライブラリや別の挿入形状を勝手に変更しない。利用したライブラリの版は記録し、新版への更新は明示操作。

Issue #15では、履歴付き保存の上流closureとtyped ID再発行を既存schemaVersion 1のまま維持し、
挿入位置XYZを選択rootごとの `shape.transform`（Move）履歴としてclosure末尾へ追加する。
配置は表示行列ではなく正本B-repへ適用する。無指定の `[0,0,0]` は従来と同じ履歴を作り、
既存entryと履歴なしsnapshotの互換を保つ。Move / Rotate / Scale / Mirrorは形状1件を明示選択し、
重なり候補からの選択を使える。複数形状を暗黙に先頭要素へ割り当てない。

ライブラリのエクスポート／インポートは正確な形状と必要定義を含むversion付き形式とする。拡張子案は`.pathloomshape`。命名は実装推奨であり、既存規約へ合わせてよい。

STEPの既存読込経路は再利用する。Issue #14で、埋込exact B-repを持つ既存STEPの明示的なCAD履歴adapterと、現在body正本のSTEP書出しを追加した。display-only meshは履歴化せず、単位・配置・正本hash・由来を保存する。プロジェクト／形状保存をSTEP書出しの成否に依存させず、3DM／F3D互換は要求しない。

### 9.3 コマンド保存

ユーザー定義コマンドは独立したversion付きデータとして保存・検索・複製・インポート／エクスポートできる。定義変更後も、既存プロジェクト内の履歴は使用した版で再計算する。ライブラリを消してもプロジェクトが壊れないよう、必要定義をプロジェクトに保持する。

## 10. 既存の生成・出力工程への接続

### 10.1 明示的な接続

- CADで形状を作っただけで、生成グラフやPrint outputへ自動配線しない。
- 「生成で使用」から対象を選び、Curve／Surface・B-rep／Solidの型に合う入力として渡す。
- 生成側は安定したCAD出力bindingと、その内側のentity参照・成功revisionを参照する。CAD側の名前変更・非表示では切れない。bindingの詳細は第18・23章。
- CADの寸法変更で成功revisionが更新されたら、参照する生成分岐だけを再計算。出力の色・ツール・速度・配置・複製・順序設定を保持する。
- CAD参照を削除した場合は、生成側を未接続／参照未解決にし、再指定できるようにする。別形状へ勝手に接続しない。
- 依存方向はCAD→生成→出力を基本とし、循環参照を作らない。生成結果をCADへ取り込む場合は、初期実装では明示的な独立スナップショットとして扱う。

### 10.2 曲線・面の変換

Curve入力は、既存処理が要求する場合にだけ指定精度で点列化する。Surface／Solidは正確なB-repのまま既存Slice等へ接続する経路を優先し、表示メッシュからの近似断面と区別する。

開曲線は閉じずに渡す。開いた面の断面も、得られた開曲線をそのまま保持できる。CAD用Contourの任意方向と、既存印刷用SliceのZ方向を混同しない。

### 10.3 検証の境界

CAD作図・保存に印刷の交差禁止、一定Z、Print height、ベッド範囲を適用しない。既存のPrint output／G-code検証は、今回のCAD追加を理由に無断で削除しない。現在の出力方式で扱えない形状は、生成・出力工程で具体的な条件を説明する。

CAD側の警告だけで生成可能な形状は流せる。一方、再計算待ち・参照未解決・カーネル失敗の古い形状を、正常な最新パスとして黙って印刷しない。

## 11. 軽快さ・負荷制御・実装構成

### 11.1 必須の処理方針

- マウス移動ごとにAIや全生成グラフを呼ばない。左の通常コマンド操作はローカルで完結。
- 長方形等の簡単な作図プレビューは軽い幾何計算で即時更新。正確な形状生成・検証が必要な処理は間引きと確定時の検証を組み合わせる。
- 重いB-rep演算・細かい再三角形分割をUIスレッドに置かない。処理要求は対象・設定・revisionだけ渡せるようにする。
- 同じ形状の正本や巨大なB-rep文字列をポインターイベントごとに複製・JSON化しない。ネイティブ側キャッシュ／セッションの形状handleを使い、保存時には永続化可能なデータへ戻す。
- プロセス常駐／再利用を検討し、ドラッグの度にPythonを起動しない。キャンセル・タイムアウト・異常終了・キャッシュ解放を実装する。
- 通信待ち・計算中でも、カメラやパネル、キャンセル操作を受け付ける。
- 通常のパラメータ変更は変更箇所と依存先だけ更新。カメラ操作や可視性変更で幾何演算を再実行しない。
- 型、有限値、参照整合性、循環等の検証は残す。理由のない固定座標・形状数上限を増やさない。
- 資源上限が必要な場合は、対象数／精度等の理由と回避策を表示。上限をCADの幾何学的禁止事項として説明しない。

### 11.2 測定目標（推奨、実機で調整）

評価機のMac機種・OS・形状数・履歴数・精度を記録する。初期目安は単純Curve100本、単純B-rep10個、履歴30操作程度。

- コマンド入力、選択、設定表示：通常操作の応答100ms以内を目標。
- 単純な作図ドラッグ：プレビュー30fps以上を目標。カメラ操作を不必要に止めない。
- 重い演算は数値目標を無理に保証せず、開始から短時間で計算状態を表示し、キャンセル可能にする。
- 再計算回数・カーネル呼出し回数・不要な全更新を計測。UIだけ速く見せて裏で全再計算する実装にしない。

### 11.3 モジュール案

`cad-document`、`cad-command-registry`、`cad-command-session`、`cad-feature-history`、`cad-reference-resolver`、`cad-diagnostics`、`cad-sketch`、`cad-sketch-solver`、`cad-shape-library`、`cad-generation-adapter`等に責務を分ける。名前・分割数は推奨。既存`app.js`や`cad-ui.js`へすべて追記しない。

カーネル操作は、入力型・設定・出力型・診断・キャンセルを持つ共通APIへ整理する。正確な形状を使う実装が未完なら、境界と未対応を記録し、ポリライン近似で偽装しない。

## 12. 実装順と工程ごとの成果物

全体として大きい変更なので、次の順で動く縦の経路を作る。各工程で必要な調査・通常の実装判断は進め、工程ごとに「次へ進めてよいか」を繰り返し求めない。ユーザー指示やローカル規則による範囲制約は守る。

| 工程 | 実装するもの | その工程の完了条件 |
| --- | --- | --- |
| P0：調査・技術検証 | 最新差分、既存テスト、共通演算境界、拘束ソルバー候補、カーネル能力、依存ライセンス | 対応能力表、採用根拠、未確認点を記録。Rectangle→Extrude→Filletの正確な形状処理と参照更新を小さく検証 |
| P1：CADの最初の縦経路 | 左端のCAD工程（合計4工程）、指定の左右配置、コマンド状態機械、Line／Rectangle、最低限の履歴、保存 | 作図→寸法編集→Undo→保存→再読込を通せる。履歴IDと参照を最初から保持 |
| P2：拘束と立体の縦経路 | スケッチ拘束・寸法、押し出し、基本Fillet、参照再指定、CAD→生成 | Rectangle寸法変更が拘束→押し出し→Fillet→生成へ追従。壊れた参照をUIから修復可能 |

| P4：面と高度な編集 | 全面作成・編集の目標範囲、Sweep／Loft／Network／Patch、Shell等 | 本書の全コマンドの実装状況を明記。適用範囲、警告、参照、保存を確認 |

推奨する実装時の成果物：本書に対応する`docs/cad-workspace-spec.md`、コマンドIDごとの実装／制限／テスト状況を持つ`docs/cad-command-status.md`、技術判断記録、依存ライセンス台帳、独自設計の参照元記録。これらの名前は推奨。リポジトリへ保存する際は、その時点の実装指示の範囲で扱う。

### 13.2 検証の実施方法

- JS単体：定義・入力手順、履歴DAG、参照、移行、診断、版管理、dirty伝播、最新応答採用。
- ネイティブ：正確な曲線／B-rep演算、開いた面、境界、スライス、成功／失敗の正本保持、保存復元。
- 実UI：選択、スナップ、数値入力、キー、ビュー、右パネル、警告から修復、4工程の往復。
- 実機：拘束ドラッグ、カーネル起動・キャンセル・再起動、ネイティブダイアログ、保存ファイル再読込、性能。
- 既存回帰：複数Print output、生成グラフ、AI編集、Grasshopper、.toolpath、出力設定とG-code。プリンター実送信は別途ユーザー指示があるときに行う。

基準commitの既存コマンドは`npm test`、`npm run test:cad-native`。Rustは現在の構成に合わせて`cargo check --manifest-path src-tauri/Cargo.toml --locked`／`cargo test --manifest-path src-tauri/Cargo.toml --locked`等を実行する。必要なランタイムがない場合は未実行と記録し、モック検証と実機検証を区別する。

単にテストが通ったことだけで全コマンドの対応を宣言しない。未実装・未検証・既知の制限を機能IDごとに残す。

### 14.1 今回の調査の位置付け

個人向けのローカルアプリであっても、コードを公開GitHubへpushする場合と完全な私的利用は区別する。基準時点のPathloomリポジトリは公開。非営利・個人利用という説明だけで、著作権・契約・OSSライセンスの条件を無条件に免除できるとは扱わない。

### 14.2 調査から採用する方針

| 論点 | 確認した内容と設計への反映 | 根拠 |
| --- | --- | --- |
| 機能・アイデアと表現 | 著作権はアイデア一般を独占する制度ではない。長方形、押し出し、コマンドからの作図等の機能を、独自コードで実装する方針とする。特定の画面・文章・コードまで自由に複製できる意味ではない | R1、R2 |
| プログラムの保護範囲 | 著作権法10条3項はプログラム言語・規約・解法をプログラム著作物の保護対象から区別する。ただし個々の命名・UI・配列の権利判断をすべて解決する条文ではなく、EULAを無効化するという意味でもない | R1 |
| 他社のソフト・資料 | RhinoのEULAはソフトウェア・付属資料の配布や、オブジェクトコードからの逆解析等を制限。公開資料から一般的な機能を理解し、Pathloom独自の仕様・実装を作る。Rhino本体の資産や非公開実装を流用しない | R3 |
| 名前・ロゴ・公式誤認 | Pathloom自身の名称を使い、Rhino／Fusionのロゴ・製品アイコンや、公式製品・提携と誤認する表示を使わない。参照が必要な場合も正確な説明に限定する | R3、R4 |

**今回行っていないこと**：Rhino／Fusionに関連する全登録特許・全登録意匠の国別調査、Pathloom名称の商標クリアランス、全ソフトウェアの同梱バイナリ検査、全Rust／Python推移依存の監査。したがって「個人用なので問題なし」「名前を変えたので絶対安全」と報告しない。

### 14.3 「模倣に見えにくく、独自設計を説明できる」実装ルール

以下は今回のユーザー希望に基づく実装条件。単なる免責文の追加で置き換えない。

1. **機能を再設計する**：公開ヘルプから必要な入力・結果を理解し、独自の機能仕様とデータモデルを作る。他社実装の複製や復元を目標にしない。
2. **Pathloomの見た目を使う**：既存の4工程へつながる独自の画面、タイポグラフィ、パネル、色、余白を使う。RhinoやFusionのスクリーンショットを下絵にしてなぞらない。
3. **素材は独自に作る**：CADタブ・コマンド・拘束のアイコンは自作SVGまたは条件を確認した素材。Rhino／Fusionのアイコン抽出、再着色、トレースは禁止。
4. **文言は独自に書く**：ヘルプ、説明、操作案内、エラー文を自分の言葉で記載。公式マニュアルの文章・画像・作例をアプリへコピーしない。
5. **コマンドは機能で整理する**：Line、Join等の一般名と日本語説明を使いつつ、一覧全体の配列やツールバーを他社製品から機械的に複製しない。特有の呼称は必要性と権利を確認し、原則は機能を表す独自名称へ。
6. **独自の価値を明確にする**：CAD→生成→パラメータ→出力の4工程、パス生成との安定参照、修復可能な履歴、作図方法を育てるコマンド定義をPathloomの設計として説明する。
7. **来歴を残す**：参照した公開URL、実装の作成者・方法、使用素材の出典と条件、既存ライブラリの変更点を記録。参考にしたという記載自体を権利処理の代わりにしない。
8. **AIへの指示も限定する**：「Rhinoの画面／コードをそのまま再現」ではなく、本書の入出力・手順・独自UIに基づいて実装するよう指示。生成コード・素材も由来とライセンスを確認する。

色やロゴを変えるだけで他社画面を再現しない。一方で、一般的な線・円・寸法・接線の記号をすべて奇抜な独自操作に変える必要はない。使いやすい一般原理と、独自に作る具体的表現を分ける。

### 14.5 Codexが実装時に行う具体作業

- 実際のnpm／Cargo／Python／vendor依存を採用版で固定し、名前・版・上流URL・SPDX表記・ライセンス原本・利用方法・同梱有無・改変有無を台帳化。
- 新規ライブラリは、導入前に利用目的と条件を調べる。条件に適合できないものは採用せず、独立実装／適合する代替案を選ぶ。
- `THIRD_PARTY_NOTICES`等とライセンス原本の格納先を整備し、Settings／Aboutから必要表示を確認可能にする。表示名だけでなく配布物に原文を保持。
- `scripts/prepare-desktop.mjs`等のパッケージ処理がライセンス、例外、必要なソース案内を除外しないか確認。
- LGPL等はJS／WASM／ネイティブ同梱・リンク方式ごとに条件を整理し、該当するソース／変更／再構築・置換の扱いを文書化。未確認を「対応済み」にしない。
- 第三者製品名を必要以上に製品UIへ表示せず、ロゴ・製品アイコンを持ち込まない。実際の相互接続がないものを「互換」「公式対応」と表示しない。
- 他社の独特なUIや技術を具体的に再現する必要が生じた場合は、特許・意匠・契約の個別確認項目として切り出す。無関係な独立機能の実装まで止めない。

ライセンス対応で利用する第三者コードの扱いが変わる場合は、その部分の設計変更理由を記録する。ライセンス不明のコードを「個人用だから」と同梱しない。

## 17. 詳細設計の固定事項と全体構成

### 17.1 今回の到達点

タブ・入力欄・ダミーの履歴ができただけの試作を完成としない。第6章の65機能IDについて、主要オプション、正確な形状、履歴再計算、参照修復、Undo、保存再読込、操作案内、診断が一体で動く状態まで進める。高度な演算には適用条件があるが、実装していない機能を「条件に合わない」として隠さない。

第12章の段階は実装の順序であり、その都度ユーザーから「次へ」と言われるのを待つための区切りではない。実装開始が承認されたら、独立して進められる残件を処理する。新たな有料サービス、外部公開、権利条件の重大な変更等が必要な場合だけ、その箇所を切り分ける。

### 17.2 採用する基本構成

| 領域 | 既定方式 |
| --- | --- |
| フロントエンド | 現行のES modules＋JavaScriptを継続。型契約はJSDocまたはスキーマで実装。今回のためにReact／TypeScriptへ全面移行しない |

| スケッチ | 独立した平面モデル。2D拘束をWorkerで解き、解いた結果を正確な曲線へ変換 |
| 履歴 | featureの依存DAG。Undo／Redo、画面のコマンドログとは分離 |
| CAD計算 | Tauriが監督する専用の永続Python子プロセス。操作名を限定したJSONL通信。既存の単発処理は互換ラッパーを残して移行 |

| `cad/persistence.js` | プロジェクト移行、資産重複排除、エクスポート／インポート |
| `cad/shape-library.js` | 形状のみ／依存履歴付き保存とID再配置 |
| `cad/generation-adapter.js` | CAD出力bindingと既存source／inputの変換・更新 |
| `native/cad_runtime.py` | JSONLループ、能力情報、形状キャッシュ、操作dispatch |
| `native/cad_operations/*.py` | curve／surface／solid／topology／serializationの幾何処理 |
| `src-tauri/src/cad_runtime.rs` | 子プロセス監督、IPC、出力制限、終了・再起動、イベント転送 |

依存方向はUI→session／document→history／native-client、solver→数値モデル、view-adapter→読み取り用document。UIが生のPythonコードを生成・実行する経路を作らない。

## 18. 正本データとIDの厳密な契約

### 18.1 ID・revision・hash

- 全IDは作成時のUUID等。名称・配列位置・表示順から生成しない。名称変更はIDに影響しない。
- `documentRevision`：確定編集、Undo、Redoごとに単調増加。Undoで過去の数値へ戻さない。
- `featureRevision`：当該featureの要求入力・設定の変更回数。計算結果は要求版と一致する場合だけ採用。
- `resultHash`：演算IDと版、パラメータ、入力の正本hash、許容差、カーネル版から算出。時刻・名称・カメラ・可視性を含めない。
- `geometryHash`：正本資産の内容hash。表示三角形・実行中handleを含めない。B-repに三角形分割が含まれる場合は、表示状態に左右されない正本のシリアライズ方式を固定する。
- `entityId`：特定featureの安定した出力slotを示す。設定変更で同じ出力slotが残る限り保持する。
- `bodyId`：編集対象としての論理的な形状のまとまり。スケッチ、開曲線、面にも使えるが、必ずSolidを意味する名前としてUIへ表示しない。
- `runtimeHandle`：CAD子プロセス内だけの参照。永続保存しない。

### 18.2 featureの保存構造

以下の型表記は契約を示すためのもので、TypeScriptへの移行要求ではない。

```ts
type JsonValue = null | boolean | number | string | JsonValue[] |
                 { [key: string]: JsonValue };
type Feature = {
  id: string;
  operation: { id: string; version: number };
  command: { id: string; version: number; mode: string };
  name: string;
  inputs: Record<string, EntityRef | EntityRef[] | SubshapeRef | SubshapeRef[]>;
  parameters: Record<string, JsonValue>;
  toleranceOverrides: Partial<TolerancePolicy>;
  outputSlots: { key: string; entityId: string; bodyId: string }[];
  featureRevision: number;
  requestedHash: string | null;
  resultHash: string | null;
  status: 'dirty' | 'running' | 'valid' | 'warning' | 'empty' |
          'failed' | 'blocked' | 'suppressed' | 'cancelled';
  diagnostics: Diagnostic[];
  lastValid: null | {
    resultHash: string;
    entitySnapshots: EntitySnapshot[];
    inputRevisionHashes: string[];
  };
};
type EntityRef = { entityId: string; role: string };
type SubshapeRef = {
  entityId: string;
  kind: 'vertex' | 'edge' | 'wire' | 'face';

```

`unknown[]`等をそのまま無検証で受理しない。実装では演算ごとにschemaを登録する。未知のフィールドを保持するか拒否するかも、各versionで統一する。

### 18.3 entityの保存構造

```ts
type EntitySnapshot = {
  id: string;
  bodyId: string;
  producer: { featureId: string; slotKey: string };
  kind: 'point' | 'curve' | 'surface' | 'shell' | 'solid' | 'compound';
  geometry: { assetHash: string; format: 'point' | 'curve-v1' | 'occt-brep' };
  closure: {
    curveClosed: boolean | null;
    surfaceUClosed: boolean | null;
    surfaceVClosed: boolean | null;
    shellClosed: boolean | null;
    enclosesVolume: boolean;
  };
  exactness: 'analytic' | 'nurbs' | 'fitted';
  accuracy: null | { toleranceMm: number; measuredDeviationMm: number;
                     measurement: 'adaptive-sampled' | 'bounded' };
  bbox: { min: [number,number,number]; max: [number,number,number] };
  visibility: 'visible' | 'hidden';
  locked: boolean;
};
```

`kind`を面数だけで判定しない。Solidは閉体積が成立することを検査する。近似で作った面も正確なB-splineデータを保持できるが、元入力を厳密に通るという意味の「完全一致」と混同しない。

### 18.4 入力形状を残す／置換する意味

幾何の正本は不変として扱う。Filletで既存B-repをその場破壊しない。新featureが入力entityを参照し、新しい出力entityを作る。

- `resultPolicy='replace'`：修正系コマンドの既定。入力を表示上隠し、論理bodyの`tipEntityId`を新しい出力へ移す。入力の正本と履歴は残す。
- `resultPolicy='copy'`：Copy、Offsetで元を残す等。別bodyを作り、入力の表示とtipを維持する。
- Join／Booleanで複数bodyをまとめる場合は新bodyを作り、元bodyとの関係を記録。Undoで元の表示とtipを復元。
- Split等で結果数が変わる場合は、由来が特定できる出力slotだけIDを引き継ぐ。左右順・bbox順で無理に同一視しない。
- 描画対象は各bodyの有効tipが基本。履歴で過去結果を選んだときだけ、その結果を一時表示する。

### 18.5 CAD出力binding

```ts
type CadOutputBinding = {
  id: string;
  name: string;
  source: { mode: 'body-result'; bodyId: string } |
          { mode: 'feature-output'; entityId: string };
  expectedKind: 'curve' | 'brep' | 'any';
  resolvedEntityId: string | null;
  resolvedResultHash: string | null;
  status: 'ready' | 'pending' | 'missing' | 'type-changed';

```

「生成で使用」の既定は`body-result`。同じ形状へフィレットを追加すると、その形状の現在結果を参照できる。過去の押し出しだけを渡したい場合は`feature-output`を明示的に選べる。bodyが複数結果へ分裂して一意に決まらなくなった場合は、候補を選ばせる。別bodyへ黙って付け替えない。

## 19. 共通演算API・ネイティブ実行プロトコル

### 19.1 演算の共通契約

全演算は`validate → resolveInputs → evaluate → inspect → publish`で実行する。結果の検証に失敗した場合はpublishしない。

```ts
type OperationRequest = {
  protocolVersion: 1;
  requestId: string;
  documentId: string;
  documentRevision: number;
  workspaceEpoch: number;
  runtimeEpoch: number;
  sessionId: string | null;
  featureId: string;
  featureRevision: number;
  requestedHash: string;
  previewSequence: number;
  intent: 'preview' | 'commit' | 'recompute';
  operation: { id: string; version: number };
  inputs: Record<string, { handle: string; geometryHash: string;
                          selector: ResolvedSubshapeSelector | null }[]>;
  parameters: Record<string, JsonValue>;
  tolerances: TolerancePolicy;
};
type OperationResult = {
  requestId: string;
  documentRevision: number;
  workspaceEpoch: number;
  runtimeEpoch: number;
  sessionId: string | null;
  featureId: string;
  featureRevision: number;
  requestedHash: string;
  previewSequence: number;
  status: 'ok' | 'empty' | 'warning' | 'failed' | 'cancelled';
  outputs: { slotKey: string; handle: string; geometryHash: string;
             kind: string; summary: unknown }[];
  topologyHistory: TopologyMapping[];
  diagnostics: Diagnostic[];
  metrics: { elapsedMs: number; cacheHit: boolean };
};
```

requestにファイルパスやPython断片を受け取らない。保存は別の限定されたコマンドで処理する。previewでも同じ演算スキーマを使い、低精度・粗い表示かどうかをintentと精度設定で明示する。

### 19.2 Tauriコマンドの入口

既存名と衝突しない以下の入口を追加する。戻り値のエラーは第24章の診断形式に揃える。

| 入口 | 引数・結果 |
| --- | --- |
| `cad_runtime_status` | 引数なし→起動状態、protocol、Python／OCP／OCCT版、演算能力、検証したオプション |
| `cad_runtime_start` | 起動・handshake。ユーザーがCADタブを開くまで遅延起動可能 |
| `cad_evaluate` | OperationRequest→受付ACK。結果・進行はイベントで返す |
| `cad_cancel` | requestId→中断要求。確定前の結果は文書へ採用しない |
| `cad_import_asset` | 検証済み正本payload／登録済みasset参照→handleと形状summary |
| `cad_export_assets` | 必要handle群→正本payloadとhash。保存時だけ呼ぶ |
| `cad_release_handles` | 使わないhandle群を解放。Undo・lastValid・表示が参照するものは保持 |
| `cad_runtime_restart` | CAD子プロセスだけを再起動。文書正本を再ロードして復旧 |

イベントは`cad-job-progress`、`cad-job-result`、`cad-runtime-state`。すべてrequest／document／feature／revisionを含める。

### 19.3 JSONL・プロセス監督

- 1行1メッセージ。`type`は`hello`、`evaluate`、`import`、`export`、`release`、`result`、`progress`、`error`等の固定集合。
- stdoutはプロトコル専用、OCCT等の通常出力はstderrへ。既存の出力リダイレクト処理を参考にする。
- 資産は最初の登録時だけ送る。演算ごとにB-rep全体を往復させない。圧縮／分割が必要なら別のchunk番号・byte数で契約する。
- Rust側は起動時に固定実行ファイルと引数配列を使い、shell経由で組み立てない。CAD実行に不要な認証環境変数は渡さない。
- Python側の1件ずつの計算キューと形状キャッシュを使う。プレビュー要求は同じsessionの最新1件だけを残す。確定要求をプレビューで追い越さない。
- 入力行・payload上限を明示し、超過は資源診断にする。初期上限は既存の対応範囲を下回らないよう測定して固定する。
- タイムアウトやプロトコル不正でもアプリ全体を落とさない。失敗jobとCAD子プロセスを切り離して再起動する。

### 19.4 中断の正確な扱い

ネイティブ計算がPythonの入力ループを塞ぐ場合、JSONでcancelを書き込むだけでは実行中処理を止められない。中断は次のように実装する。

1. クライアントはrequestを直ちに「採用禁止」にし、未実行プレビューを捨てる。
2. カーネルの協調中断が実際に動くAPIではそれを使う。対応を検証せず「キャンセル可能」としない。
3. 実行中に応答しない場合は、Rustが専用CAD子プロセスを終了させる。アプリ、Codex、プリンター通信のプロセスは終了させない。
4. handleはすべて無効化。正本資産と文書から必要なものを再ロードし、独立していたjobを安全に再受付可能にする。
5. キャンセル済みの計算をユーザーに断りなく再開しない。再計算・再試行は明示状態を伴う。

### 19.5 能力プローブ

起動時に実際のOCP版と使える演算を報告する。P0では単なる`hasattr`だけでなく、小さい形状による実行を行う。特にSweep2、NetworkSurface、Blend／Match、開いたShellの扱い、生成・修正の履歴取得を確認する。

現行OCCT 7.8系にない新APIを、最新版ドキュメントに名前があるだけで呼ばない。薄い`occt_compat.py`等へ版差を隔離する。カーネルの更新が必要なら、既存のSTEP・スライス・保存とライセンス条件の回帰を確認してから採用する。

## 20. コマンドの状態機械と入力の詳細

### 20.1 共通状態

| 状態 | 入力と遷移 |
| --- | --- |
| `idle` | 名前／別名を入力→`collecting`。事前選択があれば対応する入力slotへ仮投入 |
| `collecting` | 現在slotの点・形状・数値を受け取る。必要数が揃えば次slotへ。複数選択はEnterで終了 |
| `previewing` | プレビューと設定を編集。まだ文書featureは作らない。設定変更でsequenceを増やして再評価 |
| `committing` | 入力を固定して正確な結果を検証。二重確定・追加クリックを無効化し、カメラ操作は維持 |
| `repairing` | 成立しない設定を保持して対象再指定／値変更。正常な元文書を維持 |
| `committed` | 正式トランザクションを1件追加→`idle` |
| `cancelled` | sessionの仮形状と選択だけを破棄→開始前の文書を保持して`idle` |

コマンド起動だけでUndoを増やさない。session内の戻る操作は文書のUndoと別。右上の数値変更はこのsessionへ送り、DOMから直接featureを書き換えない。

### 20.2 入力slot

各slotは`key`、`kind`、`allowedEntityKinds`、`minCount`、`maxCount|null`、`ordered`、`allowPreselection`、`prompt`、`default`を持つ。点slotはクリック位置だけでなく、スナップ先のSubshapeRefも保持できる。

事前選択は型・数が適合する場合だけ使う。不適合な選択は保持したまま「曲線を選択してください」等で次の入力を案内する。複数対象の順序が重要なLoft等は、番号付きで表示し、右上から並べ替え可能にする。

### 20.3 数値・座標パーサ

- スカラーは符号付き小数、指数表記、`mm`／`cm`／`m`、角度の`deg`／`rad`を受け付け、内部単位へ変換。
- 座標は`x,y`、`x,y,z`。スケッチ中の2成分はローカル平面、自由作図の3成分はWorld。
- `@dx,dy,dz`は直前の確定点からの相対入力。直前点がない場合は起点を選ぶよう案内。
- `Enter`で未入力の既定値を選べるslotと、入力必須slotを区別する。
- 数式評価のために`eval`を使わない。初期仕様は単位付き数値で十分。四則演算を追加する場合は限定grammarのパーサを使う。
- 表示上の丸め値と内部精度を分ける。入力値を勝手に印刷層高へ丸めない。

### 20.4 代表的な入力手順の固定

| コマンド／モード | 入力順 | 途中で設定できる値 |
| --- | --- | --- |
| Rectangle／2 corners | 平面→対角点A→対角点B→確定 | 幅、高さ、角丸、平面。Aを基準に寸法変更 |
| Rectangle／center | 平面→中心C→コーナーP→確定 | 幅=2×ローカルabs(P−C)、高さ、中心、向き |
| Rectangle／3 points | 点A→辺端B→反対辺の位置P→確定 | ABの長さと軸、直交方向の高さ |
| Line | 始点→終点／方向と距離→確定 | 座標、長さ、方向 |
| Circle／center radius | 平面→中心→半径→確定 | 半径／直径、中心 |
| Join | 適合形状群→Enter→結果確認→確定 | 許容差、接続グループの採用 |
| Extrude | 曲線／面→Enter→方向／距離→確定 | signed距離、両側、Cap、元を残す |
| FilletEdge | エッジ群→Enter→半径→確定 | 半径、接線連鎖の追加、元を残す |
| Sweep1 | レール→順序付き断面群→Enter→結果確認 | フレーム、向き、継ぎ目、Cap |
| Sweep2 | レールA→レールB→断面群→Enter | 対応点、向き、境界側、Cap |
| Loft | 断面群→Enter→順序・向き確認→確定 | smooth／ruled、閉じる、継ぎ目、Cap |
| BooleanDifference | 残す形状群→Enter→工具群→Enter→確定 | 工具を残すか |
| Shell | ボディ→除去する面群→Enter→厚み→確定 | 内／外、厚み、元を残す |
| Trim | 切断要素群→Enter→削除する区画を選択→Enter | 切断要素を残す、延長を使うか |

Rectangleの平面は現在の作業平面を既定とし、毎回の選択を要求しない。Extrudeの既定方向は平面輪郭の法線、非平面Curveでは方向の指定を求める。Trim等の複数区画選択は、誤削除前にプレビューで戻せるようにする。

## 21. スケッチ拘束ソルバーの実装仕様

### 21.1 モデルと変数

スケッチは`plane={origin,xAxis,yAxis}`を持つ。直交・正規化を検証し、`zAxis=xAxis×yAxis`。world点は`origin+u*xAxis+v*yAxis`。拘束は原則このu,v上で解く。

| 要素 | 未知数と保持データ |
| --- | --- |
| Point | u,v。参照専用点と駆動点を区別 |
| Line | 始点／終点のpoint ID。共有点は同じ未知数を使い、重複座標で模擬しない |
| Circle | 中心point ID、半径。内部最適化は正半径を保つ変数変換が可能 |
| Arc | 中心point ID、半径、始角、sweep角。向きと採用する弧のbranchを保持 |
| Ellipse | 中心、2軸半径、回転角。軸の入れ替わりで突然反転しない |
| NURBS | 制御点、次数、knots、multiplicities、weights。初期の拘束編集はknots／weightsを固定し、制御点を未知数にする |
| Construction | 正確な補助線／補助点として存在するが、既定の輪郭出力から除く |

スケッチを作るために曲線を自動的にpolylineへ変換しない。任意3D曲線はスケッチの外で編集可能。3D形状をスケッチへ参照する場合は、投影・交差・断面のどれを使ったかを明示する。

### 21.2 残差の定義

共通の点をp=(u,v)、線方向をd=b−a、円中心をc、半径をrとする。以下は独自実装する数式仕様であり、特定CADのコードを流用しない。

| 拘束 | 残差／実装規則 |
| --- | --- |
| 一致・点点 | `p.x−q.x`、`p.y−q.y`の2残差 |
| 点が線上 | `(p−a)×unit(d)`。線分の範囲内かは別に評価。無限延長線と区別 |
| 点が円上 | `norm(p−c)−r`。Arcでは角度の範囲・branchも検証 |
| 水平／垂直 | `b.y−a.y`／`b.x−a.x` |
| 平行／直交 | `unit(d1)×unit(d2)`／`unit(d1)·unit(d2)`。零長線は解決前に診断 |
| 等長／等半径 | `norm(d1)−norm(d2)`／`r1−r2` |
| 同心 | 円中心のu,v一致 |
| 固定 | 対象要素の独立変数を最適化対象から除外。固定時の値を保持 |
| 距離 | `norm(p−q)−target`。符号付き水平／垂直距離は成分差を使う |
| 半径／直径 | `r−target`／`2*r−target` |
| 角度 | `atan2(cross,dot)−target`をbranchに沿って連続化。±π境界で跳ねない |
| 点対称・軸対称 | 中点が対称軸上にあること、2点差が軸に直交すること。軸上で一致する場合の退化も検出 |
| 接線・線円 | 接触点が線と円上にあり、線方向と半径が直交。円側だけ動くと仮定しない |
| 接線・円円 | 指定接触点の一致と接線方向一致。内接／外接branchを保持 |
| 接線・一般曲線 | 指定した曲線parameterで位置と単位接線を比較。必要ならparameterも未知数。端点接続か途中接触かをデータに保持 |

一般曲線のparameterを勝手に別の接触点へ飛ばさない。接触点を再指定できるようにする。G2曲率拘束はスケッチの必須目標ではなく、Blend／Match等の面・曲線操作の連続性として別処理する。

### 21.3 計算方法

既定の実装は、warm start付きの非線形最小二乗＋減衰Gauss-Newton／Levenberg方式とする。

1. 拘束グラフを連結成分へ分け、変更要素に接続した成分だけを取り出す。
2. 変数を現在形状の代表長Lでスケーリング。距離残差もLで除し、角度はradを使う。自由度の報告は元単位で解釈する。
3. 初期値は最後の成功解。最初だけ現在の作図値を使う。全点を原点や乱数へ戻さない。
4. 基本拘束のJacobianは解析微分。一般NURBS等は中央差分で補助可能。差分幅は`max(1e-8,abs(x)*1e-6)`等をスケール後に適用し、勾配チェックをfixtureで行う。
5. 線形stepは拡張行列`[J; sqrt(lambda)*D]`の最小二乗として求める。正規方程式の逆行列を明示計算しない。Householder QR＋列pivot等、rankを扱える手法を使う。
6. 改善したstepだけ採用し、悪化時はlambdaを増やす。`D[j]=max(1,norm(Jの第j列))`を初期の減衰scaleとする。初期`lambda=1e-3`、改善時1/3、悪化時×10を既定とし、測定で調整可能。
7. 欠けた自由度は、前の解からの変化が小さい解を優先。位置維持のためにユーザーに見えない固定拘束を追加しない。
8. hard拘束を満たした上でドラッグの希望位置へ近づける。ドラッグ目標はsoft条件。到達不能でもhard拘束を壊して指へ追従させない。
9. commit時はhard残差を第24章の許容範囲で再検証。費用関数が小さいだけでは成功にしない。

初期実装で数値線形代数が不安定な場合、既存の検証済み実装や小規模ライブラリへ置き換え可能。ただしソルバー全体を他社製品からコピーしない。依存を増やす場合も第14章の条件と計測を通す。

### 21.4 反復・時間予算

- ドラッグ：1回の計算予算12ms程度、最大15反復を初期値とする。Workerは短い区切りで最新要求を受け付ける。
- 確定：最大200反復、通常の小規模スケッチで1.5秒を初期予算とする。重い場合は進行・中断・対象削減の案内を表示。
- 収束しない場合は「矛盾」と断定せず、数値未収束、退化、矛盾候補を区別する。
- 時間・反復上限は資源制御であり、要素数に関する永久的な作図禁止として扱わない。
- 未拘束の点は動かせる。完全拘束の点は移動を抑え、「寸法／拘束を編集」へ案内。

### 21.5 自由度・矛盾・冗長

- hard Jacobianの数値rankを求め、独立変数数−rankを残存自由度の目安にする。特異形状では局所的な値であることを詳細欄に示す。
- 固定値は変数から除外。ユーザーに見えない拘束でrankを水増ししない。
- 新規拘束で失敗した場合、まずその拘束を除いたときに元解へ戻るか確認する。関連残差・Jacobianから衝突候補を絞る。
- 候補を一時除去して再計算し、解ける組合せを診断に使う。ただし数学的な最小矛盾集合を証明していなければ「候補」と表示。
- 冗長拘束はhard条件を壊さず追加できる場合に警告。冗長を矛盾と同じ扱いにしない。
- 診断中もユーザーが各候補を選択・抑制できる。最初の拘束を勝手に削除して解決しない。

### 21.6 dimensionのデータ

寸法は`id`、`kind`、`refs`、`value`、`unit`、`mode='driving'|'reference'`、`labelPosition`を持つ。参照寸法は未知数を駆動せず、成功形状から算出。駆動→参照へ変更すれば拘束が一つ外れる。寸法ラベルのドラッグは配置変更であり、形状を再計算しない。

### 22.7 Sweep／Loftの必須処理

**Loft**：入力順序を固定し、各curveの向きと閉曲線の継ぎ目を個別に持つ。wireのedge数が違う場合、互換化を試す前に入力copyを作る。kernelが入力wireを変更する設定を持つ場合、正本へ影響させない。結果がねじれる場合は順序・向き・継ぎ目のどれを直すか案内する。

**Sweep1**：レールの接線フレームと断面の基準平面を記録。レールの不連続、曲率ゼロ付近、閉レールの継ぎ目を検出。断面を任意の最寄り位置へ自動投影せず、接続stationを選べるようにする。初期目標は1本の連続レールと1つ以上の断面。

**Sweep2**：単なる姿勢補助レールと、2本の実境界レールを区別する。初期必須fixtureは、各断面の両端が2レール上にある開曲線群。レールの対応を単調なparameterとして作り、断面ごとの幅・姿勢・形状を保つ。採用版のauxiliary-spine／contact-on-border等で満たせる場合に使い、使えない場合は2境界と断面を制約にしたsurface構成を実装する。閉断面の場合は、各レールと対応する断面上の点を追加指定する。2レールへの偏差と断面への偏差をそれぞれ検証する。

### 22.8 NetworkSurface／Patchの必須処理

NetworkSurfaceは2方向のfamilyを明示的に選択し、曲線を順序付け、各交点のparameter対応を求める。交点が欠ける、同じ交点が複数ある、順序が逆転する場合は該当ペアを表示する。

実装経路は、対応する曲線網からGordon型のsurface構成、または曲線制約付きtensor-product B-spline fitを行う。後者は近似として扱い、入力曲線を指定精度以内で再現できることを確認する。boundaryだけを通るLoftで内部familyを無視しない。

PatchはCurve／Pointの近似surfaceとして独立させる。曲線網が成立しなかったからといってNetworkをPatchへ無断置換しない。近似する場合は明示的な操作・精度表示を伴う。

精度検証はparameter空間を一度だけ粗くサンプルする方法で終えず、曲率や誤差の大きい区間を追加サンプルする。保証された誤差上界でない場合は`adaptive-sampled`として記録し、「厳密な最大誤差」と表示しない。

### 22.9 Blend／Matchと連続性

- G0：位置偏差。G1：単位接線／法線の角度。G2：接続方向の曲率の差を検証する。
- 端部の向きとsurfaceのorientationを揃えて比較し、法線の符号反転を不連続と誤認しない。
- Curve BlendはBezier／NURBSの端部位置・1階・2階微分条件から構成する。
- Surface Blendは2境界と横断方向の微分条件を持つHermite／Coons／B-spline patch等で構成。境界に沿うparameter対応を保持。
- Matchは変更側の境界付近の制御点列を調整し、参照側の位置・方向・曲率へ合わせる。変更範囲と離れた側を保持する設定を提供。
- 最初の必須fixtureは未トリムNURBS境界で成立するG1／G2。トリム境界では基底面の再構成や局所patch等が必要になる場合があるため、扱える方式を実装・記録する。制約を満たせない結果をG2成功としない。
- 近似結果を残せる場合は、要求条件からの偏差を示し警告付きでユーザーが採用可能。ただし完成判定の必須fixtureは要求精度・連続性を満たすこと。

### 22.10 コマンドごとの検査・履歴

各演算は必ず、正確な結果、出力slot、入力からのtopology mapping、計測した誤差、警告・失敗理由を返す。通常の作図でも方向・平面・入力方式を保存する。作図中に入力した点を、確定後に単なる最終bboxへ置換しない。

### 22.11 パラメータ名・単位・schemaの固定

## 23. 再計算・参照修復・Undoの処理順

### 23.1 新規作成と既存feature編集

新規作成では、正常な結果またはユーザーが採用する警告付き結果が得られてからfeatureを追加する。失敗sessionは修正可能なdraftとして残せる。

既存featureの編集では、ユーザーが設定変更を確定した時点で「要求された設定」のトランザクションを保存してよい。計算に失敗した場合は、その設定とfailed状態を保持し、幾何だけはlastValidへ戻す。これは正常結果のpublishとは別。今回の変更を取り消す操作で、元の設定・状態へ戻せるようにする。

未確定の数値を打つたびに正式履歴を更新しない。文字列のdraft、プレビュー、確定した要求設定、成功形状を別に持つ。保存時にはdraftも保持できるが、下流がdraftを正常な形状として利用することはない。

### 23.2 再計算アルゴリズム

1. 変更patchをschema・ID・参照・循環について検証する。循環するpatchは適用せず理由を表示。
2. 変更したfeatureのrevisionを増やし、依存先をDAGで走査。変更されない枝へdirtyを伝えない。
3. 必要入力がreadyでないfeatureはblocked。原因feature IDを一つ以上保持。
4. readyなfeatureを安定した順序で評価。入力hashと設定hashが既存cacheと一致すれば結果を再利用。
5. 正常結果とtopology mappingを検証し、そのfeatureの出力slotとentityを更新。
6. 対象bodyのtipと出力bindingを解決。bindingがreadyへ変わったものだけ生成側へ通知。
7. 結果hashが変わらない場合は、下流の不要な幾何評価を省略可能。表示名等のmetadata更新とは分離。
8. 一つの枝が失敗しても、独立してreadyな枝の処理を継続。

featureの抑制は、原則としてその出力を利用不可にする。Filletを抑制して入力bodyを見せる等のpassthroughは、演算が明示的に定義している場合だけ使う。JoinやBooleanで適当な入力1個を代わりに渡さない。

### 23.3 応答採用の条件

結果採用前に次を照合する。

- 開いている文書IDと`workspaceEpoch`が要求開始時と同じ。
- CADランタイムの`runtimeEpoch`とhandleの所属が同じ。
- featureがまだ存在し、要求されたfeatureRevisionとrequestedHashが一致。
- 現在の入力正本hashがrequest時と一致。
- previewの場合はsession IDとpreviewSequenceが最新。
- requestがキャンセル・破棄済みでない。

**globalのdocumentRevisionが増えただけでは、無関係な枝の正常結果を捨てない。** documentRevisionは監査と順序確認に使い、採用の可否は上記の依存内容で判断する。逆にUndo後に数値が同じでも、キャンセル済みrequestの結果を安易に採用しない。

捨てた結果のhandleは参照数を確認して解放。文書、lastValid、表示、Undoが利用している資産を解放しない。

### 23.4 安定参照の実装レベル

新規プリミティブには意味のあるsemantic pathを付ける。

| 形状 | semantic path例 |
| --- | --- |
| Rectangle | `corner/00`、`corner/10`、`corner/11`、`corner/01`、`edge/uMin`等 |
| Extrude | `cap/start`、`cap/end`、`side/<sourceEdgeId>` |
| Box | `face/xMin`、`face/xMax`、`face/yMin`、`face/yMax`、`face/zMin`、`face/zMax` |
| Circle／Arc | `center`、`start`、`end`、curveのparameter参照 |
| Sweep／Loft | 断面ID・レールID・生成区間の由来。単なるface indexを使わない |

既存STEPはインポート時の正本hashとsubshape対応表を保存し、編集時のカーネル履歴から更新する。外部STEPを別ファイルへ差し替えた場合まで同じIDと決めつけない。

resolverの優先順位：

1. 同じ正本hashのtopology IDが存在する。
2. 同じsemantic pathの出力が一意に存在する。
3. 実演算のModified／Generated対応が一意で、型と隣接等を満たす。
4. 上記で証明できない場合はfingerprintで候補を探すが、原則としてユーザーの再選択を求める。

fingerprintには型、幾何種別、長さ／面積、重心、bbox、法線／接線、隣接、元featureの由来を含める。これらは検索・順位付け用。最も近いというだけで自動決定しない。分裂して複数の候補になった場合は「1つ／複数を採用」を操作の入力型に合わせて選べるようにする。

### 23.5 参照修復UIの一連の動作

`対象を選び直す`→対象featureをrepair modeで開く→該当bodyのみを選択可能にする→元参照の種類と候補を表示→ユーザーが新対象を選ぶ→結果をプレビュー→確定→参照patchを1件記録→下流再計算。

再選択中のEscは参照を変更せずrepair modeを終了。元featureの失敗状態は残す。「上流の編集を取り消す」は、無関係な後続操作を乱暴にまとめてUndoせず、原因の要求設定を指定トランザクションで戻す。

### 23.6 Undo／Redoと削除

- 1コマンドの成功確定、1回の寸法確定、1回の拘束追加／解除、1回の参照再指定を1トランザクションとする。
- マウスドラッグはpointerdown時をbefore、pointerup時をafterとして1件。毎フレームのpatchを積まない。
- transactionは追加／更新／削除された定義と表示tipのbefore／afterを持つ。巨大B-repはhash参照で共有し、Undoごとに全文複製しない。
- Undo／RedoはdocumentRevisionを増加し、影響jobを無効化。復元できるcacheを使い、必要な枝だけ再計算。
- 削除で未解決になる参照を事前表示。ユーザーが依存先を残すことを選んだら、存在しない対象をschema違反としてファイル全体から拒否せず、typedなunresolved参照として保存する。
- 削除したIDを別の形状に使い回さない。Undoで元IDを復元する。

## 24. 許容差・診断コード・復旧アクション

### 24.1 初期許容差ポリシー

| 設定 | 初期値・単位 | 意味 |
| --- | --- | --- |
| `kernelLinearMm` | 1e-6mm | 正確な幾何の照合・成立判定の基準。Join許容差と同一にしない |
| `joinLinearMm` | 0.01mm | ユーザーが接続を許す境界距離。操作ごとに保存 |
| `fitLinearMm` | 0.01mm | Loft等の近似・Patch／Network fitの要求精度。実際の測定誤差も返す |
| `solverLinearMm` | 1e-6mm | hardなスケッチ距離拘束の残差閾値 |
| `angularRad` | 1e-5rad | 通常の方向・接線検証の初期閾値 |
| `selectionRadiusPx` | 8 CSS px | 点・線の選択とスナップ候補の近さ。ズームでモデル許容差へ固定変換しない |
| `previewDeflectionMm` | 0.1mmを目安 | 通常プレビューの三角形近似。モデル尺度と画面誤差も考慮 |

| `generationSamplingMm` | 0.02mmを初期値 | 生成側へ点列を渡す場合の明示的な近似設定 |

G2の曲率差はモデル尺度に依存するため、固定の無次元閾値だけで判定しない。絶対曲率差と相対差、境界の位置・角度誤差を計測して結果に保持する。

## 25. 保存形式・移行・回復の詳細

### 25.1 top-levelとCAD領域

`.pathloom`の`format='pathloom'`を維持し、top-level versionを2にする。既存のsources、instances、importedShapes、printer、設定等の意味を維持する。その上に`cadDocument`を追加する。

次は**CAD領域だけの最小サンプル**。既存projectの必須フィールドを省いた完全な`.pathloom`ファイルとしては使わない。

```json
    "documentRevision": 0,

    "tolerances": {
      "kernelLinearMm": 0.000001,
      "joinLinearMm": 0.01,

    "outputBindings": [],
    "draftSessions": [],
    "uiState": {
```

空文書でruntime未起動なら`kernel.version`はnullでよい。正本B-repを保存する場合は実行時の版を入れる。project schema version、CAD schema version、演算version、command versionは別物。

### 25.2 資産の保存

`assets[hash]`は`format`、`encoding`、`byteLength`、`data`、`sourceKernelVersion`を持つ。正本は、point／解析Curve／NURBSの構造化JSON、またはB-repの標準シリアライズ。初期はUTF-8 B-rep文字列を既定とし、圧縮する場合はencodingに明記する。

三角形・線分の表示cacheは`displayCache`へ分離し、省略しても正本から復元できる。cacheは正本hash・表示精度・renderer版で検証する。

保存に含めるもの：現文書で必要なasset、lastValid、未知の演算でも保持すべき正本、必要なcommand定義。含めないもの：runtimeHandle、requestId、access token、Keychain、個人の一時パス、実行中プロセスID。

Undoスタックをそのままファイルへ丸ごと書くことは必須にしない。作成履歴と失敗・draftの復元は必須。再起動後のUndoを提供する場合は、容量と互換の契約を別途固定する。

### 25.3 読込処理

1. ファイルbytesを一時領域で読む。サイズ・JSON・format・versionを確認。
2. version 1は既存validatorへ通し、CAD領域がないversion 2の内部状態へ移行。元を自動上書きしない。
3. version 2は既存領域とCAD領域を別々に検証。既存領域をversion 1の意味として確認するadapterを用意し、旧validatorの先頭checkだけを乱暴に削除しない。
4. ID重複、dangling参照、循環、資産hash、数値、使用定義の版を検証。意図的なunresolved参照はtypedな状態として許す。
5. runtimeへ必要資産を登録し、正本を検証。unsupported kernel等は読み取り・回復モードを提示。
6. 正常に復元できることを確認してから現ワークスペースを置換。キャンセル・エラーなら元作業を保持。

古いファイルを移行して保存するときはユーザーに新形式になることを表示。Save asで別名保存可能にする。変更のない読込だけでファイルを自動書換しない。

### 25.4 原子的保存とautosave

- 保存snapshotのdocumentRevisionを固定し、必要な資産を集める。保存中に新編集が入った場合は、保存済み版より新しい変更が残る状態を表示。
- 書込は同一ディレクトリの一時ファイル→flush→置換を基本。元ファイルを先に削除しない。
- autosaveはapp-data内の回復用ファイル。ユーザーのprojectを勝手に上書きしない。確定変更後のidle時にまとめて保存する。
- 初期値は変更後1秒以上idle、頻度は最短10秒に1回。大きい資産はhash単位で再利用し、ドラッグごとに全文serializeしない。
- autosaveには最後に成功した形状と現在のdraft／失敗設定を区別して含める。次回起動時に回復／破棄を選べる。
- 保存失敗を「保存済み」と表示しない。元の作業と回復候補を保つ。

### 25.5 形状・コマンドライブラリの移送

形状だけの場合は正本asset、単位、基準点、名称、表示情報を含める。履歴付きの場合は、対象の依存を逆向きに走査し、必要feature／sketch／constraint／definition／assetを閉包として含める。外部参照が残る場合は、取り込む／固定snapshotへ変える／保存を取り消す、を選べるようにする。

挿入時は全IDの写像を作り、schemaでID参照と定義された箇所だけを置換する。一般の文字列へ一括置換をかけない。basisと単位を指定し、挿入用transformを一つの履歴として残す。

コマンドdefinitionは版を固定して保存。alias衝突では既存を上書きせず、新名／別名／採用中止を選択。標準コマンドへ同名を付けても標準定義を消さない。

## 26. 画面・選択・生成連携のイベント契約

### 26.1 DOMと工程名

新工程の内部名は`model`、タブIDは`modeModel`、専用パネルIDは`modelPanel`を既定とする。既存の`cadPanel`は生成工程で使われているため、その意味を黙って新CADへ置き換えない。

`modeModel`、`modeGenerate`、`modeParameters`、`modeOutput`をこの順で並べる。tablistのroving tabindex、aria-selected、aria-controlsを更新し、キーボードで4工程へ移動可能にする。既存canvasを二重生成しない。

CAD工程のgridは左／中央／右。左幅280px、右幅320pxを初期値とし、最小幅は左220px・右280px程度を目安に可変化。右は上55％を設定、下45％を履歴として初期化し、分割位置を保持する。viewportが狭い場合はパネルを折りたためるが、機能を消さない。

### 26.2 状態の所有者

| 状態 | 所有する層 |
| --- | --- |
| 正確な形状・feature・body・拘束 | CadDocument／native runtime |
| 未確定の入力・選択slot・プレビュー | CommandSession |
| 表示camera・hover・gizmo | ViewAdapter |
| 確定した選択・workplane・panel幅 | Workspace UI state。保存するものと一時状態を区別 |
| エラーと解決アクション | feature／sessionのdiagnostics。UIはそれを表示するだけ |
| native job受付・runtimeEpoch | NativeClient／Tauri supervisor |

DOMのinput値を唯一の正本にしない。右上の設定はstateから描画し、変更イベントはsession／transactionへ送る。タブを切り替えたことだけでgeometryを再生成しない。

### 26.3 イベント表

| イベント | 送る先と動作 |
| --- | --- |
| `command.start` | registryを解決→session開始。事前選択の型を評価 |
| `viewport.pick` | sessionが入力待ちならslotへ、待機中ならselectionへ |
| `viewport.move` | 必要なsessionだけpreview要求。hover表示だけで再計算しない |
| `setting.change` | draft更新。数値が成立する場合だけpreview。文字入力途中の`-`等で警告を連発しない |
| `setting.commit` | create／editの規則に従って確定と再計算 |
| `history.select` | 対象を強調→右上へそのfeatureの設定を表示 |
| `history.repair` | 対象input／subshapeの再指定session開始 |
| `constraint.add/remove` | sketch transaction→影響成分だけsolve→正確な曲線更新 |
| `dimension.dragLabel` | UI位置だけを変更。幾何jobなし |
| `cad.bindingChanged` | 接続された生成inputだけinvalidate。次の生成を予約 |

| `project.open` | 全jobを旧workspaceEpochとして無効化→検証済み新文書へ切替 |

### 26.4 hit testとスナップ

- 左クリックはCADの選択／作図を優先。カメラ操作は現行の体系を確認し、CAD入力と競合しない右・中ボタン等へ割り当てる。操作ガイドに明示する。
- マウス移動が3 CSS pxを超えた場合はdragとして扱い、単純clickの確定と区別する。右drag回転後にcontext menuを出さない。
- 点／edgeは画面上の距離でpick。faceはraycast後にtriangle-to-face mapで正確なsubshapeへ変換。
- mapにはentityId、resultHash、runtimeEpochを付ける。古いmeshのface番号を新B-repへ使わない。
- 隠れたshapeは通常pickしない。重なった候補は種類・名称を短い一覧で選択可能。
- 面／edge／点のフィルターは一時的に切替可能。後のコマンドに不可視の選択制限を残さない。
- スナップは候補と種類を表示。通常の位置スナップは座標参照であり、勝手に永続拘束へしない。関係を保持するモードを明示ONにした場合だけ拘束・履歴参照を追加し、glyphを表示。
- 自己交差・開放境界のマーカーは選択可能だが、通常選択を遮らない。診断表示のON/OFFを用意。
- 旧結果をghost表示している場合は「更新前」と表示し、新しい操作の正本入力に黙って使わない。明示的なsnapshot化は別操作。

### 26.5 gizmoとスケッチのドラッグ

通常の3D移動gizmo、スケッチ点の2D移動、寸法ラベル移動を区別する。スケッチ点dragは平面交点→soft目標→拘束solve→previewの順。完全拘束なら形状を動かさず、関係する寸法を表示する。

faceの押し引きは、そのfaceの法線と距離を基本にし、既存の汎用object移動と区別する。切り離して移動する場合はモードを表示。Solidを保つことが成立しないときも、別の開いた結果を明示的に採用できる処理があるなら選択肢として示す。

### 26.6 生成入力の拡張

新しい入力定義案は次のとおり。既存inputの型を流用する場合も、同じ情報と検証境界を保持する。

```json
{
  "id": "input-cad-1",
  "type": "cad-reference",
  "name": "Case Body",
  "bindingId": "binding-body-1",
  "geometryKind": "brep",
  "sampling": {"toleranceMm": 0.02},
  "status": "ready"
}
```

`cad-reference`を追加する場合は、validator、graph port、AI context、workerの入力解決、project保存、library保存、UI表示の全経路を更新する。定義に新型を追加しただけで完了にしない。

- Curve bindingはCurve portへ接続。既存のJS演算が点列を必要とする境界だけでsampleし、要求精度・閉／開・元の正本参照を保持。
- B-rep bindingは既存のSurface／B-rep系入力へ解決。Slice等には正本asset／handleを渡し、表示meshを正本として使わない。
- WorkerがTauriを直接呼べない場合は、現在のnative queue経路で入力を準備してからworkerへ渡す。main threadで重い幾何計算をしない。
- 同じbindingとrevisionとsampling設定なら変換cacheを共有。
- AIには、型・名称・bbox・必要な幾何summaryと参照IDを送る。巨大B-rep文字列や全履歴を毎回送らない。
- CAD側のbodyの名前・可視性・パネル移動はパスの再生成を起こさない。
- bindingがmissing／pendingなら、その入力に依存する分岐だけを待機にする。別の正常分岐の編集は継続できる。
- 出力ファイルの対象に未解決分岐が含まれる場合は黙って除外せず、除外する対象をユーザーが明示できるようにする。

### 27.3 数値判定の注意

- bboxや面積だけで別形状を同一としない。Curveはparameter評価・端点・接線、Surfaceは境界と内部評価、Solidはvalidity・閉体積・面／edge関係も見る。
- 再計算後の面番号が同じことを正解にしない。意味のある参照が維持できたかを検証する。
- `result.ok=true`が返ったことだけをテストしない。求めた幾何・拘束・連続性が成立したことを数値で確認する。
- 誤差を測っていない近似に0を記録しない。測定不能はnullと診断で示す。

`docs/cad-command-status.md`等に、65IDそれぞれについて次の列を持つ。

`ID / UI・入力 / 正確な幾何 / 主要モード / 拘束との連携 / 履歴再計算 / 参照修復 / Undo / 保存 / 警告・失敗 / fixture / 実UI確認 / 既知制限`

各欄は`done`、`partial`、`not-started`、`not-applicable`と根拠を記録。fixture名を付ける。未実装や未検証を空欄にしない。「not-applicable」は当該機能に不要な理由がある場合だけ使う。

## 28. Codexの実行手順・再開単位・最終指示

### 28.1 開始直後に行うこと

1. AGENTS.md、git status、最新履歴、現行の起動・テスト経路を確認。未commit変更を保持。
2. 本書の65IDとA／T／R条件を作業台帳へ展開。着手前から全残件を見える形にする。
3. 小さな実行プローブでOCP／OCCT、保存、面・edge履歴、スケッチ解法を確かめる。
4. 既存UI・生成・保存から変更する接点を特定し、最初の縦経路を実装。
5. P1だけで止めず、基本曲線→拘束・立体→面・編集→ライブラリ→統合の順に作業を進める。

### 28.2 1機能の実装ループ

各機能は次の単位で閉じる。

`schema・入力定義 → 正確な演算 → 正常／失敗fixture → session・preview → 履歴・参照 → Undo・保存 → 診断アクション → UI確認 → 対応表更新`

見た目を全部並べてからbackendを後で作る順序にしない。共通基盤ができたら同系統の演算はまとめて実装できるが、全経路の確認を省かない。

### 28.3 難しい演算に遭遇したとき

- API名が見つからない場合はカーネルが提供する基礎演算を調べ、独自の組み合わせで同じ機能を満たせるか検証。
- 新版カーネルの機能を使う場合は、版差adapter、旧asset、保存、依存条件を先に評価。
- 数学的に無理な入力は適用条件と修正方法を説明する。実装不足を入力のせいにしない。
- 一機能の研究中でも、他の独立した残件は進める。未完の高難度機能は台帳へ具体的な問題・試した手法・次の検証を残す。
