# アプリ制作の憲法

**作業の見通しを保ち、少ない手数で、自分の意思で試し続けられる。**

初版 v1.0 · 2026年10月20日

本書は、アプリ改善時のフィードバックから抽出した、企画・設計・実装・検証の共通判断基準である。実装中に迷ったとき、機能追加で画面が複雑になったとき、同じ指摘を繰り返し受けたときに立ち戻る。

## 0. この憲法の使い方

本書を機能の追加理由にせず、必要な機能をどう実現するかの判断に使う。個別アプリの仕様や実装許可を、この文書だけから補わない。

適用する環境の上位ルールに従い、製作者からの最新の明示指示と合意済み仕様を優先する。その範囲で、第1〜10条を判断基準にし、具体的な見た目や配置には後述の「初期方針」を使う。

- **原則**：複数の制作を通じて守りたい、目的と判断基準。
- **初期方針**：過去の好みから、最初の案に採用する方針。用途や検証結果で変更できる。
- **個別仕様**：そのアプリ・その機能のために決めた振る舞い。他のアプリへ自動適用しない。

実装前は「今回の目的・触る対象・保つ状態」を整理する。実装後は該当する条文と確認項目で、実際の操作を検証する。例外が必要なら、適用範囲と理由を仕様に短く残す。通常の実装判断に、毎回の追加承認を要求しない。

### 迷ったときに戻る10項目

1. 主役となる作業へ、画面と注意を使う。
2. 同じ意味の設定・概念を重ねない。
3. 対象を直接触り、一連の仕事を短く完了できるようにする。
4. 文脈に応じて情報を出し、作業位置は安定させる。
5. 配置・まとまり・動きに、操作上の意味を持たせる。
6. 同じ操作の表現を揃え、重要なものをはっきりさせる。
7. 操作への応答を先に返し、最新の結果へ正しく追従する。
8. 作る自由を保ち、必要な段階で必要な制約をかける。
9. 手間を自動化し、利用者の判断と既存の作業を守る。
10. 保存・再開・出力・実利用まで通して、完成を確かめる。

### 実装者・AIへ渡すとき

本書をプロジェクトの参照文書として置き、実装依頼で参照先を指定する。置いたことだけで自動適用されるとは考えない。指示の例：

> 実装前に「アプリ制作の憲法」を読み、今回の目的と変更範囲に当てはめてください。最新の明示指示と個別仕様を優先し、関係する原則を使って設計・実装・確認を進めてください。見た目の初期方針を固定仕様にせず、関係のない変更を広げないでください。完了時は、変更点・確認結果・未確認事項を簡潔に報告してください。

## 第1条　主役となる作業に、画面と注意を使う

画面ごとに、いま何を見て、何を判断し、何を変える場所なのかを明確にする。その作業に必要な対象・結果・操作へ、面積と視線を配分する。

### 実装の判断

- 形状を調整するなら、結果を確認しながら操作できる。業務一覧なら、比較したい項目を見渡せる。
- 見出し・説明・管理情報・装飾は、判断への寄与に応じて小さくする、移す、または省く。
- 画面を切り替える場合も、いまの対象や結果とのつながりを保つ。工程による表示切り替えは、目的が明確なら使う。
- 「削る」判断と「必要な機能を残す」判断を両立する。情報不足を、見た目の簡潔さとして扱わない。

**確認**：最も大きく目立つものは、いま扱う対象か。比較や判断のために、何度も画面を往復させていないか。

## 第2条　同じ意味を、重ねて持たせない

設定や概念の責任範囲を揃える。アプリ内部の都合で生じた名前や分類を、利用者が覚える前提にしない。

### 実装の判断

- 全体設定・対象ごとの設定・機器設定など、何に効く値かを明確にする。
- 同じ値を複数箇所で変更できるなら、共通の値として同期する。別の値なら、違いと優先順位がわかるようにする。
- パラメータを連動させたら、参照元を明らかにし、連動先の直接編集を制御する。解除方法も用意する。
- 用途を増やさず概念だけ増やす変換工程、重複メニュー、同内容の説明を減らす。
- 名前は、利用者が扱う対象・行為に合わせる。分類は作られ方だけで分けず、使う目的で整理する。

**確認**：どこで設定すればよいか一意に判断できるか。新しい用語や段階は、実際に異なる役割を持つか。

## 第3条　対象から直接操作できるようにする

頻繁な操作は、対象と操作箇所を近づける。実行前のモード選択、別画面への移動、同じ条件の再入力を必要以上に挟まない。

### 実装の判断

- 値を触って調整する、対象をドラッグする、ステータスを押して変更するなど、対象と行為を対応させる。
- 細かな設定は、詳細表示やコンテキストメニューにまとめる。日常操作を、その中へ隠さない。
- ステータス・担当・コメントなど、一つの仕事として扱う変更は、一連の操作で完了できるようにする。
- 初期表示の生成など、利用者の意図が明らかな処理は自然に始める。毎回の実行ボタンを惰性で置かない。
- ドラッグ・ホイール・ショートカットは、対象環境で発見・操作できる形にする。ホバーのない端末では常設操作やタップなどの入口を確保する。

**確認**：やりたい対象を見つけた場所から操作を始められるか。削除したボタンの代わりに、使える入口があるか。

## 第4条　表示は文脈に合わせ、作業位置は安定させる

操作中に、対象の位置・大きさ・選択・表示段階が理由なく変わらないようにする。必要な情報の出し入れが、作業のやり直しを生まない構造にする。

### 実装の判断

- スクロールバーの出現、詳細の開閉、数値の桁数、読み込み完了で、周囲の操作位置を不用意に動かさない。
- 一覧から詳細へ進み、戻ったときに、対象・絞り込み・スクロール位置など必要な文脈を保つ。
- パラメータ編集のために、ノードやカード全体の大きさを毎回変えない。
- 状況に合わない操作は、非表示か非活性を選ぶ。対象との関係を理解するために必要なら、非活性のまま残す。
- キャンバスに境界や制限があるなら、必要性を検討し、残すものは認識できるようにする。見えない壁を作らない。

**確認**：操作のたびに目と手が対象を探し直していないか。戻る・再表示・再開で、続きから作業できるか。

## 第5条　配置・まとまり・動きで意味を伝える

階層、親子関係、クリックの対象、処理の流れを、構造から理解できるようにする。動きは、何がどう変わったかを伝えるために使う。

### 実装の判断

- まとまり単位と操作単位を揃える。月号全体を開くなら、その月号全体が反応する。
- インデント、余白、並び、区切りで、対象とその詳細の関係を表す。
- 入出力の型や役割は、実際の接続口に対応して示す。離れた凡例や曖昧な「In / Out」だけに頼らない。
- 対象の拡大や表示の連続性で、一覧から詳細への移行を理解できるようにする。
- ちらつき、不要なホバーの色変化、操作を待たせる演出を避ける。動きを減らす設定にも対応する。

**確認**：どの範囲を押すと何が起きるか伝わるか。アニメーションを入れた理由を、操作上の意味で説明できるか。

## 第6条　表現を揃え、重要度には差をつける

同じ意味の操作は、同じ形・アイコン・挙動で表す。重要な結果・状態・主要操作には、十分な強さを与える。

### 実装の判断

- 展開矢印、削除、追加、選択、ダイアログ、メニューなどの表現を、新機能でも既存ルールに揃える。
- アイコンだけで理解できる場合は簡潔にする。曖昧なアイコンにはラベルや補足を添え、支援技術向けの名前も持たせる。
- 色・太さ・面積を使う箇所を絞り、選択状態・主要アクション・判断に重要な差へ優先配分する。
- 色だけに意味を背負わせない。選択や状態は、形・位置・文字などでも確認できるようにする。
- 数値、単位、小数点、桁、列の位置を揃える。利用者が理解しやすい単位へ変換して表示する。
- 囲み、背景、影、説明を足すときは、それぞれが必要か判断する。淡くしすぎて読めなくしない。

**確認**：同じ操作が違う見た目になっていないか。最初に目に入るものと、重要なものが一致するか。

## 第7条　操作への応答を先に返し、重い処理を整理する

入力の受け付け・操作中の表示・最終計算を分けて考える。結果の計算が重くても、手元の操作は続けられるようにする。

### 実装の判断

- スライダー、入力値、選択、ドラッグの反応を優先する。入力のたびに不要な画面全体の作り直しをしない。
- 連続した変更はまとめ、最新の入力を処理する。古い計算結果で、新しい状態を上書きしない。
- 計算中は必要に応じて前の結果を保ち、更新待ちであることを伝える。古い結果を最新として扱わない。
- 起動時や保存済みプロジェクトの再開時も、必要な初期表示を自動で整える。値を一度変更しないと表示されない状態を残さない。
- 外部通信やAIは必要な場面で使う。確定済み処理の数値調整は、可能な範囲でローカルに実行する。
- 出力時は、最新状態の計算・検証が完了していることを確かめる。待機・失敗時に何をすればよいか示す。

**確認**：連続して操作しても入力が重くならないか。画面の値・プレビュー・保存結果・出力が、同じ状態を指しているか。

## 第8条　作る自由を保ち、制約は必要な段階へ置く

編集・生成・出力の各段階で、必要な条件を分ける。中間データへ最終出力専用の条件を持ち込み、表現や再利用を狭めない。

### 実装の判断

- CADの中間処理なら、Curve・Point・Surfaceなど必要なデータを扱えるようにする。印刷条件は、印刷への変換や出力の段階で評価する。
- 表示や内部実装の都合から生じた制限を、利用者の能力の上限として固定しない。
- 条件を設ける場合は、守る対象と適用範囲を明確にする。継続できる注意と、継続できないエラーを分ける。
- 明確な不正データ、データ破損、実機の危険につながる出力などは、該当段階で止める。自由度を理由に、根拠ある保護を一括で削除しない。
- エラーには、問題の対象、原因、直す場所を示す。内部名や未定義値をそのまま利用者へ出さない。
- AIへの入力は目的に必要な情報へ整理する。不要な巨大データを毎回渡す設計で、利用を行き詰まらせない。

**確認**：その制約は、いまの段階で必要か。エラーを読めば、どこをどう直すかわかるか。

## 第9条　自動化は、利用者の判断と既存の作業を守る

繰り返しの手間を減らしながら、何を変更するかの主導権を保つ。明示された変更対象以外へ、影響を広げない。

### 実装の判断

- ファイル更新の追従や初期計算など、意図の明確な定型処理は自動化できる。
- ノードの接続、既存構成の組み替え、設定の上書きなど、意味を変える自動操作は、合意した仕様の範囲で行う。
- AIによる部分編集は、関係のない形状・接続・名前・分類・配置・設定を維持する。
- 変更前にかけた調整を、別の設定変更で不用意に失わない。失敗時は元の状態を保ち、切断・解除・やり直しなど必要な修正手段を用意する。
- データ更新で選択中の対象を勝手に移動・削除・並べ替えしない。そうする仕様なら、理由と結果が理解できるようにする。

**確認**：便利な自動化のために、利用者の意図を決めつけていないか。変更範囲と保持する状態が明確か。

## 第10条　実際に使う流れが通って、完成とする

画面に機能があることと、利用者の仕事が完了することを区別する。保存・再開・書き出し・連携先での利用まで、変更に関係する一連の流れを確認する。

### 実装の判断

- 保存した設定・プロジェクト・再利用部品が、再起動後にも意図した状態で使える。
- 表示上の位置・形状・単位などが、保存データや生成ファイルへ正しく反映される。
- 外部連携では、相手側が必要とする形式・座標・サムネイル・情報も確認する。ファイルが生成できたことだけで完了にしない。
- ウィンドウの縦横比、縮小、全画面、長い名前、項目数の増加でも、必要な操作が届く状態を保つ。
- 既存操作の退行を確認する。新機能のために、ドラッグ、メニュー、サイズ変更などを壊さない。
- 検証は変更の影響に合わせる。実際の操作・代表データ・必要な自動検証を使い、未確認の実機動作や環境は明記する。

**確認**：利用者が実際に使うところまで通したか。未確認の範囲を、完了したものとして伝えていないか。

## 初期方針：最初のデザイン案に適用すること

以下は過去の好みを反映した出発点であり、全アプリ共通の固定仕様ではない。

| 項目 | 初期方針 | 適用時の判断 |
| --- | --- | --- |
| 配色 | 白・明るい中立色を基調にし、主要操作や状態へアクセントを使う | 読みやすさ、対象物の見え方、利用環境に合わせる |
| パネル | 軽い浮遊感、必要に応じた半透明と控えめなぼかし | 透過で文字や背後の対象が読みにくくなるなら調整する |
| 装飾 | 囲み線・影・背景の重ね掛けを抑える | まとまりを伝えるために必要な線や背景は残す |
| 文字 | 管理IDや補足は控えめにし、対象名・状態・数値を読み取りやすくする | 必要なラベル、単位、識別情報まで省かない |
| パネル密度 | 主作業の表示面積を確保し、詳細設定は必要時に開く | 毎回読む内容は開いておく。コンパクト化で操作しづらくしない |
| 追加・削除等 | 頻度の低い補助操作はホバーやメニューも使う | タッチ操作やキーボード操作で入口を失わない |
| アニメーション | 関係・選択・遷移を理解するための軽い動き | 固定の時間・透過率・ぼかし値を憲法として指定しない |
| 定型機能 | OS標準の保存ダイアログ、メニューバー、既知の操作慣習を活かす | プラットフォームと利用者に合う場合に採用する |

## 原則が競合したときの判断例

| 迷う場面 | 判断の仕方 |
| --- | --- |
| 説明を消すと、初見で操作がわからない | 対象付近に必要なラベルや補足を残す。情報削減は理解を損なわない範囲で行う |
| 毎回読むメモを、画面整理のために畳みたい | 読む頻度を優先して表示する。折りたたみは詳細設定など必要な場面へ使う |
| 主要な二つのコマンドを、一つのプルダウンにまとめたい | 両方を頻繁に使うなら並べて表示する。コントロールの数だけで簡潔さを評価しない |
| カードを縮めると、入力や選択が難しくなる | 操作できる大きさを確保し、不要な余白や重複情報を先に整理する |
| 自動接続すると手数が減る | 接続が表す意味を利用者が決める機能なら、合意した場合だけ行う。明示的な接続・切断を用意する |
| 最新の形状計算が重い | 入力と表示の応答を先に返す。最終計算の完了まで、出力状態を明確にする |
| 開いた曲線や立体的な曲線が、印刷条件に合わない | 中間の編集では保持し、印刷対象へ変換する段階で用途に合った条件を確認する |
| 「わかりやすくする」ために新しい画面・分類を追加したい | 既存の概念・場所で表せるか先に確認する。追加により実際の判断や操作が改善する場合に採用する |

## 実装の進め方

### 着手前

1. 今回の利用目的と、完成後に通るべき操作を短く定義する。
2. 最新の明示指示、合意済み仕様、今回の変更範囲を確認する。
3. 保持する対象・設定・選択・データと、影響を受ける既存機能を整理する。
4. 該当する条文を選ぶ。既存のUI表現とデータ構造を確認する。
5. 未確定でも容易に変えられる配置や見た目は、初期方針から具体案を作る。意味が変わる重要な曖昧さだけ確認する。

### 実装中

- 触って比較できる単位で作り、実行中の画面へ反映する。
- 一つの指示を理由に、関係のない色・配置・名称・挙動まで変更しない。
- 試して変わった仕様は、新しい意図へ更新する。途中の案と最終仕様を混在させない。
- 同じ指摘が繰り返されたら、該当箇所に加えて、共通部品や設計上の原因も確認する。
- 「あとで実装」「まだ変更しない」「提案のみ」など、依頼の段階を守る。GitHubやSitesの更新は、明示された実装・更新依頼の範囲で行う。

### 完了前の確認

- [ ] 目的の操作を、入力から結果の利用まで通した。
- [ ] 不要な説明、設定の重複、役割の曖昧な概念が増えていない。
- [ ] 同じ操作のアイコン、メニュー、展開表示、選択表現が揃っている。
- [ ] 主要情報と補足情報の強弱、数値と単位の揃え方を確認した。
- [ ] 開閉・スクロール・入力・ウィンドウ変更で、位置のずれ、重なり、切れが起きない。
- [ ] 連続操作中も反応があり、古い処理で最新状態を上書きしない。
- [ ] 対象外のデータ・設定・接続・既存操作を維持している。
- [ ] 関係する保存・再開・出力・外部連携を確認した。
- [ ] 制約やエラーの適用段階と、利用者に示す直し方を確認した。
- [ ] 変更点・検証結果・未確認事項を整理し、許可された範囲で試せる状態にした。

変更が小さい場合は、影響する項目だけを確認する。無関係な検証を、完了のための儀式として増やさない。

## この文書を育てるルール

- 新しいFBは、まず個別仕様・初期方針・原則のどこに属するか整理する。
- 単発のボタン位置やサイズ変更を、そのまま全アプリ共通の条文にしない。
- 共通原則を更新する際は、発言・場面・困りごと・求める結果を根拠として残す。
- 製作者の発言、実装側の提案、編集者による解釈を区別する。提案されたことだけで、採用済みの原則にしない。
- 矛盾して見えるFBは、利用場面・頻度・対象・試作段階の違いを確かめる。過去の指示を理由に、現在の意図を固定しない。
- 更新履歴には、変えた条文と理由を残す。憲法の変更によって、既存アプリの実装を自動で変更しない。
